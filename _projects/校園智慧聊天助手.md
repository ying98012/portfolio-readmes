# 🎓 SchoolGPS - 校園智慧助手

## 📘 專案簡介

**SchoolGPS** 是一款專為校園情境設計的 Android 室內導覽應用。

一般地圖 App（Google Maps、Mapbox Directions）只懂「戶外道路」，到了學校大樓裡就完全失靈：GPS 飄移到隔壁棟、不知道你在幾樓、也算不出「從一樓樓梯口走到四樓 408 教室」這種路線。

SchoolGPS 解決的就是這件事：

- 在教學大樓的多個樓層之間做**室內導航**
- 自動判斷使用者**目前所在樓層**
- 把 GPS 飄移到走廊外的點**吸附回真實走廊**
- 用一個 AI 助手回答**校園相關問題**（教室、社團、開放時間）

整個 App 以 **Kotlin + Jetpack Compose + Mapbox** 打造，沿用 **MVVM** 三層架構。

---

## 🏗️ 系統架構（MVVM）

| 層 | 角色 | 範例 |
|----|------|------|
| **View（UI）** | 純 Jetpack Compose，只負責畫面與事件 | `MapScreen`、`ChatAssistantScreen`、`SettingsScreen` |
| **ViewModel** | 業務邏輯與狀態管理（StateFlow） | `MapViewModel`、`BleViewModel`、`AuthViewModel` |
| **Model / Data** | 感測器、Firebase、Room、地圖路網 | `IndoorGraph`、`WifiScanner`、`FootprintRepository` |

整個專案沒有任何 XML 佈局，全部用 Compose。資料層用 Coroutine + Flow，UI 用 StateFlow 觀察。

## 🎯 核心問題與解決方案

> 這是這份 README 的重點區，每一節都是一個「我們遇到什麼問題、為什麼難、最後怎麼解」的故事。

### 問題 1：室內 GPS 飄移嚴重，定位點常常飛到走廊外

**問題：**
GPS 訊號穿不進混凝土，室內 accuracy 動輒 20–30 公尺。原始定位點會跳到牆外、隔壁棟、甚至建築外的停車場，導航完全沒辦法用。

**解法：兩段式吸附**

1. **教室中心吸附**：每間教室 Polygon 都有預先標好的幾何中心（`center_lng`/`center_lat`）。當使用者選中某間教室作為起點/終點時，App 強制把定位點**吸附到該教室中心**，而不是用浮動的 GPS。
2. **走廊吸附（snap-to-corridor）**：非導航時，把目前定位點**投影到「同樓層最近的走廊邊」**，距離 ≤ 8 公尺才吸附。這條藍點看起來會貼著走廊走，不會穿牆。
   - 這個吸附只用於**顯示**，不會寫回足跡資料庫，避免污染採集精度。

**效果：** 即使 GPS accuracy 20 公尺，地圖上的藍點仍會穩定地貼著走廊移動。

### 問題 2：怎麼知道使用者在幾樓？GPS 沒有 Z 軸

**問題：**
GPS 只有經緯度，不知道你在 1F 還是 4F。但室內導航必須切換到正確的樓層底圖，否則畫面顯示的是 1F 但你實際在 4F，整個體驗就崩了。

**解法：三來源仲裁 + 防抖切換**

| 來源 | 原理 | 適用情境 |
|------|------|---------|
| **WiFi BSSID + RSSI** | 在每個樓層蒐集校園 AP 的 BSSID（MAC 位址），實測時挑訊號最強的 AP 對照樓層表 | 一般使用者，零硬體 |
| **ESP32 + BMP280 氣壓** | 樓層之間有約 1.2 hPa 氣壓差，在 1F 校準一次後可精確推算 1F～8F、B1～B2 | 進階使用者 / 採集者 |
| **手機內建氣壓 sensor** | 讀取 Android `TYPE_PRESSURE`，做為沒有 ESP32 時的備援 | 自動 fallback |

由 `BleViewModel` 統一仲裁這三個來源。為了避免**邊界區 WiFi 訊號穿透**造成樓層在 3F/4F 間來回跳：

- **Sticky margin**：要切到新樓層必須比舊樓層 confidence 高出一定門檻
- **快速路徑**：如果同一樓有 ≥3 顆 AP 命中、且最強 RSSI ≥ −65 dBm，直接信任、跳過防抖

**效果：** 一般情境 4–8 秒就能切到正確樓層；邊界區也不會亂跳。

### 問題 3：Mapbox Directions API 只支援戶外道路，室內路徑怎麼算？

**問題：**
教室之間的導航不能用 Mapbox 官方 Directions API，因為它只認得馬路。我們需要自己定義「走廊在哪、樓梯在哪、教室在哪」，再自己跑最短路徑。

**解法：自建室內路網圖 + Dijkstra**

1. **路網資料來源**：`assets/indoor_graph.json` 手工定義走廊節點（交叉口、樓梯口、電梯口、走廊補充點）與同樓層連線。
2. **教室節點動態注入**：教室節點不寫死在 JSON 裡，App 啟動後從 Mapbox Studio 的教室 Polygon 中讀取 `node_id` 與中心點，**執行時注入**到路網圖。好處是教室資料**單一來源**（只在 Mapbox Studio 改一次）。
3. **邊權重用 Haversine 距離**：JSON 裡的 `weight` 不用（採集步數會跳號），改用兩節點 GPS 距離計算真實長度。
4. **Dijkstra 最短路徑**：算出 A → B 的最短走廊路徑，回傳一串節點。
5. **決定性 tie-breaking**：當多條路距離相同時，用「節點 ID 字典序」做第二排序鍵，確保**相同輸入永遠產生同一條路線**（避免使用者每次點都看到不同的路）。

**路線繪製：**
路徑算出來後轉成 GeoJSON LineString 疊到 Mapbox 地圖上，**地圖只顯示目前選取的那一條**（不會同時顯示樓梯與電梯兩條讓畫面糊掉）。

### 問題 4：跨樓路徑會「上樓走 A 樓梯、下樓走 B 電梯」的混用問題

**問題：**
最一開始版本用 Dijkstra 直接算跨樓最短路徑，結果常出現「從 1F 走樓梯 A 上 3F、再從 3F 搭電梯 B 下 4F 終點」這種奇怪路線。使用者根本不可能照走，因為一座樓梯只通到 7F、一座電梯只通到 5F，跨樓中段切換樓梯/電梯實際上要走回轉角。

**解法：豎井（Shaft）三段式規劃**

把每一座物理樓梯或電梯抽象成一個「豎井（StairShaft）」，由節點的 `shaft_id` 欄位識別（例如 `STAIR_A`、`ELV_L`）。同一座樓梯在每一樓的節點共用同一個 `shaft_id`。

跨樓規劃改為**三段式**：

```
段 L1：起點 → 豎井入口（同樓層 Dijkstra）
段 L2：豎井內部從起樓垂直步進到目標樓
段 L3：豎井出口 → 終點（同樓層 Dijkstra）
```

關鍵設計：

- **L1 / L3 強制封鎖對立類型的垂直節點**：「走樓梯」選項在 L1/L3 完全封鎖電梯節點，反之亦然。整段路保證**只用同一座樓梯**或**只用同一座電梯**。
- **同樓層也封鎖樓梯/電梯中繼**：當起終點同樓時，自動禁止 Dijkstra 經由樓梯口/電梯口繞路，避免「明明同一層走 5 公尺就到，卻繞去樓梯口再繞回來」的怪路線。

**結果：** App 提供使用者「走樓梯」「搭電梯」**兩條獨立的最短路線**選項，每條都絕對乾淨。

### 問題 5：學校根本沒有現成的室內地圖數據，怎麼建立？

**問題：**
Mapbox / Google 上不可能找到「中興大學工程館四樓平面圖 + 教室座標」這種資料。學校總務處提供的 PDF 平面圖只有相對尺寸（施工圖性質），沒有真實 GPS 座標。

**解法：QGIS 地理參考 + Mapbox Studio Tileset**

```
學校 PDF 平面圖（沒有 GPS）
        ↓
QGIS 地理參考（用已知的教室四角 GPS 當錨點，把平面圖對齊到真實世界）
        ↓
在 QGIS 上沿著平面圖描繪每間教室 Polygon
        ↓
匯出 GeoJSON，每間教室補上屬性：
  - classroom (教室編號，如 E442)
  - name (中文名稱)
  - floor (樓層)
  - node_id (對應路網節點 ID)
  - center_lng / center_lat (中心點，給吸附用)
        ↓
上傳到 Mapbox Studio 各樓一個 Tileset（NCUT_1F、NCUT_2F ... NCUT_B2）
        ↓
App 啟動後自動讀 Style，每個樓層當作一個 Layer，由 visibility 控制顯示
```

**樓層切換用 Visibility 而非 Filter：**
切換樓層時，把不需要的圖層 `visibility` 設為 `none`。比 Filter 過濾更快，因為 GPU 直接跳過整個 Layer，記憶體中只保留當前樓層的 tile。

### 問題 6：如何不手動逐點採集，就能擴充室內路網？

**問題：**
室內路網 JSON 一開始要逐個節點現場 GPS 採集，效率極低。每多一棟樓就要工讀生繞 100 個點，不可能規模化。

**解法：自動足跡 + 候選邊 Promote 流程（仿高德地圖）**

```
1. 使用者在地圖上正常走動（開啟「紀錄足跡」開關）
   → 每隔幾秒採樣 GPS，存到 Room 資料庫（footprint.db）
   → 同一條連續移動為一個 segment

2. 累積到一定資料量後，按「完成這次採集並更新路網」
   → 系統自動把足跡點「匹配」到現有走廊節點
   → 沒匹配到的點聚合成「候選邊」（pending_edges 審核池）

3. 候選邊符合最小品質門檻才 promote 進正式路網：
   - 至少 3 條不同的 segment 經過
   - 平均 GPS accuracy < 12 公尺
   - 信心分數 ≥ 0.6

4. 通過門檻的邊輸出到 indoor_graph_promoted.json
   下次啟動 App 時優先讀這份「升級版路網」
```

地圖上同時提供**採集進度 Overlay**：灰色 = 既有走廊邊；黃色 = 已收集 < 3 段；綠色 = 達標可 promote。讓採集者一眼看出哪些走廊還沒走夠。

**效果：** 一般使用者「走著走著」就能持續擴充路網，不需要專門的採集人員。

### 問題 7：AI 助手怎麼回答校園相關問題？

**問題：**
校園問題（圖書館開放時間、社團聯絡方式）有兩種：
- 已知 FAQ：應該秒回標準答案，不該丟給 AI 隨便編
- 未知問題：丟給 AI 模型回答（但有 API 額度限制）

**解法：兩層回答策略**

```
使用者問問題
    ↓
1. 先比對 Firebase Realtime Database 上的 FAQ 表
   - 精確比對（用戶問句 == FAQ 問題，含「包含」雙向）
   - 關鍵字比對（用戶句子包含任一 keyword）
    ↓ (沒命中)
2. 交給 Gemini API（含對話歷史，最近 10 輪）
   - 額度由 Firebase 綁定使用者帳號管理（每人 50 次）
   - 額度用完可貼自己的 Gemini API Key 無限使用
```

**特殊處理：**
- Firebase Console 輸入的欄位名稱常常**帶不可見空格**（全形空格、不斷行空格），所以做了 Unicode key normalize
- 回覆中的 URL 自動偵測並以**藍色底線**渲染（用 Compose 新版 `LinkAnnotation.Url` API），點擊以系統瀏覽器開啟

### 問題 8：使用者登入要怎麼做？要支援 Google 嗎？

**解法：Firebase Authentication 四種流程**

| 流程 | 技術 |
|------|------|
| Email + 密碼登入 | `signInWithEmailAndPassword` |
| Email 註冊 | `createUserWithEmailAndPassword` + 自動寄驗證信 |
| 忘記密碼 | `sendPasswordResetEmail` |
| Google Sign-In | Android Credential Manager → `GoogleIdToken` → Firebase Credential |

**重點設計：**

- 註冊後**必須通過 Email 驗證信**才能進入主應用（防止假帳號）
- Google 登入直接視為已驗證
- 入口判斷：`MainActivity` 根據 `AuthViewModel.currentUser` 是否登入且驗證過，自動決定顯示 Auth NavGraph 或主應用 NavGraph，無須手動導航

## 🧭 室內導航完整流程（演示用）

```
1. 使用者在搜尋框輸入「E442」
   → 即時搜尋所有樓層的教室索引

2. 選定目標教室
   → 自動切換地圖到該教室所在樓層（4F）
   → 鏡頭飛到教室中心

3. 按下「導航到這裡」
   → 起點 = 目前定位（吸附到最近走廊）
   → 終點 = E442 教室中心

4. 系統計算路線：
   - 同樓 → 單一最短路線
   - 跨樓 → 提供「走樓梯」與「搭電梯」兩個選項

5. 使用者選擇路線
   → 地圖只顯示選中的那一條（GeoJSON LineString）
   → 顯示距離、預估時間、換樓方式圖示
   → 樓梯/電梯節點上自動顯示對應圖示（依當前檢視樓層過濾）

6. 開始導航
   → 相機飛至路線起點
   → 跨樓時可手動切樓層預覽其他樓層的路線段
```

## 📌 設計原則

- **單一資料來源（Single Source of Truth）**：教室資料只在 Mapbox Studio 維護一份；登入狀態只在 `AuthViewModel` 管理。
- **室內外路由完全分離**：戶外用 Mapbox，室內用自建 `IndoorGraph`，絕不混用。
- **可離線運作的核心功能**：路網與底圖支援本機快取，無網路也能查教室與規劃路線（僅 AI 助手與 FAQ 需要連線）。
- **決定性演算法**：相同輸入永遠產生相同路線，方便除錯與回測。
